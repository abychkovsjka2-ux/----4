# Відповіді на питання (практична робота 4)

Номер мого варіанта: 1

1. Які коди стану й винятки обробляє моя функція і чому саме так?
Перед відправкою запиту функція перевіряє аргумент item_id: якщо це не ціле число (включно з bool) або воно менше за 1, виникає ValueError без звернення до мережі, щоб не витрачати час і ресурси на завідомо хибні запити. Якщо сервер повертає код 200, функція розбирає JSON, але якщо в тілі відповіді прийшов не JSON (наприклад, HTML), перехоплює помилку декодування й кидає ValueError("Відповідь не є JSON"). Код 404 обробляється як нормальний результат пошуку — функція повертає None, бо запису просто немає в базі. Усі інші коди стану (наприклад, 400, 429, 500, 503) викликають RuntimeError з кодом помилки, щоб повідомити про збій. Мережеві винятки (тайм-аут або відмова з'єднання) не перехоплюються, щоб програма вищого рівня сама вирішувала, чи повторювати запит.
2. Що б сталося з моєю програмою без `timeout` і без перевірки коду стану?
Без параметра timeout запит у бібліотеці requests може чекати на відповідь нескінченно довго, тому при зависанні сервера програма просто заблокувалася б і зависла. Без перевірки коду стану requests не викидає винятків на помилки 404 чи 500. Програма спробувала б обробити відповідь про помилку як звичайні дані: замість None при 404 повернула б словник зі службовим повідомленням про помилку, а при 500 чи 503 з HTML-сторінкою впала б із незрозумілою помилкою розбору JSON.
3. Чим мій розв'язок відрізнявся б, якби API було справжнім і недоступним протягом хвилини?
Зараз функція робить лише одну спробу запиту й одразу падає при збої мережі або статусі 503. Для реального API, яке може тимчасово лежати хвилину, потрібно додати цикл повторних спроб (retry) з експоненційним збільшенням паузи між запитами та врахуванням заголовка Retry-After від сервера. Оскільки простий інтервал у 1–2 секунди за 3 спроби не перечекає хвилинний збій, довелося б збільшити кількість спроб або інтервали очікування до 15–30 секунд, перехоплювати мережеві винятки (Timeout, ConnectionError) і, за можливості, повертати збережені раніше дані з кешу.
